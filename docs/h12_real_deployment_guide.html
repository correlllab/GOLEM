Native Linux / ROS 2 Humble / Real robot

H1-2 Real
Deployment Guide

A staged procedure template for the onboard control computer and a companion computer. Use existing components, separate observation from actuation, and qualify each hardware stage before proceeding.

Procedure template, not hardware validated by this work. This work implements comparison and simulation tests only. No real robot commands were run to create this guide. Team approval, a tested physical E-stop, and physical start-pose approval are required before hardware control. Counter and its planned comparison batch are not yet hardware certified. A passing import, offline test, or simulation is not permission to actuate.

01 / Scope

Read the whole guide before connecting to the robot. Commands below are templates for an approved operator, not a hardware acceptance report. The missing approvals, calibration files, policies, and limits must be supplied by the responsible team. There is no ready-to-run, hardware-qualified common Frame/Counter configuration supplied here.

start_position_verified:=false is not a universal actuator interlock. The full h12_real_robot_bringup.launch.py still launches safety and upper-arm initialization; that flag gates only the lower-body controller and estimator. Upper initialization and lower pre-positioning can move joints before any action goal or policy confirmation.

This guide chooses one staged component flow. Do not also launch either full real bringup. The standard onboard launch includes drivers, navigation, state, control, and gated legs. The companion h12_real_desktop_bringup.launch.py includes AI model servers, YOLO enabled, skills, and RViz; it is not a lean marker-only entry point. An established team may choose those full bringups instead, but then must not add duplicate components from this page.

The root helpers run_simulation.sh, run_experiment.sh, run_ros.sh, and run_rviz.sh under scripts/ are simulation only and reject domain 0. Do not use them on the real system, bypass their guards, or add an allow-real helper. Use native ROS commands below only after preflight. Do not run a simulator on the hardware bus.

03 / Native Setup

Do this with the hardware disconnected or under the team's non-actuating maintenance procedure. Start in the host's own GOLEM checkout. An administrator must provide Ubuntu/ROS Humble, system Python 3.10, the packages in environments/ros/apt-packages.txt, ROS DDS-IDL generators and required message packages (including nav2_msgs interfaces). Do not run whole-workspace rosdep or install the AI/Nav2 runtime for this lean workflow.

Check both machines. The same Ubuntu version does not guarantee Pinocchio, Crocoddyl, OMPL, Torch, or native wheel ABI compatibility on an ARM onboard computer. The locked controller setup uses binary wheels and disables source builds. If the architecture is unsupported, stop and obtain an approved build and numerical validation for that architecture; do not replace pins or assume x86 checks qualify ARM.

Initialize submodules and obtain Git-LFS assets through the team's checkout process. Set GOLEM_ROOT to this host's absolute checkout path. Leave Conda before setup; repeat deactivation for nested environments, and skip it if Conda is absent or inactive.

The existing experiment profile selects 12 packages, including the control, safety, interface, lower-policy, marker skill and localizer packages. It is reusable native infrastructure, not a hardware-driver installer. No simulator environment is needed on the robot. Offline setup checks do not certify hardware operation.

Hardware additions

  • The experiment profile does not build cl_realsense. Provide an approved installation of that package and external realsense2_camera, matching librealsense, USB permissions and image-transport plugins. Confirm the actual head camera serial; the repository launch hardcodes one unit.
  • Building magpie_control does not install all physical Dynamixel/OpenRB prerequisites or udev rules. Approve servo communication, motor calibration, serial permissions and stable left/right device IDs before launching its drivers. Driver initialization may actuate grippers.
  • The physical E-stop serial bridge requires the correct device, permissions, wiring, status polarity and independent physical stop test. ROS status alone does not prove a working emergency stop.
  • Use the team's approved driver stack, or a manually selected package build only after confirming its exact source and dependencies are available. This page deliberately supplies no guessed driver install/build command. Livox/navigation are not needed for the lean marker experiment; if used separately, follow their approved stack without changing the pinned Livox submodule.

04 / Preflight

  1. Obtain team approval for the hardware, software revisions, operator roles, physical safety rig, workspace exclusion area, fall risks, and stop/power sequence. A qualified person must hold the physical E-stop. Verify its behavior independently of ROS action cancellation.
  2. Verify the robot's physical start pose, support, joint/hand clearances and payload. Empty both hands for initial control and comparison qualification. Mechanical rig verification and a later freestanding benchmark are separate experiments; neither is established by this guide.
  3. Verify the actual hardware-facing NIC, link, addressing and DDS configuration on each host. Do not assume eno1 exists or reaches the robot. Match raw Unitree DDS domain 0 and ROS domain 0, approved RMW/Cyclone settings, discovery and clock synchronization. Do not change a NIC or DDS URI by guesswork.
  4. Assign exactly one final rt/lowcmd writer: the approved safety relay. The upper controller writes only rt/safety/lowcmd_upper_in; the lower role writes only rt/safety/lowcmd_lower_in. Check raw DDS ownership using the team's approved method, not just ROS graph topic counts. No other vendor controller, old process or second bringup may compete.
  5. Approve matching real upper/safety configs: motor mapping, gains, joint/velocity/torque limits, stale-data behavior, E-stop handling, NIC/domain and Counter settings. Inspect effective Counter limits after all controller, publisher and safety clipping, not just nominal solver limits. Use the same approved common config for both comparison conditions.
  6. Approve the policy and lower YAML with their owner: checkpoint, physical startup pose, IMU trim, command limits, confirmation behavior and support procedure. APPROVED_LOWERBODY below is a policy selector, not a file path. Bundled ALMI/FAME simulation and offline checks are not real-robot approval.
  7. Verify fresh measured state, TF and camera timestamps before motion. All hardware nodes use wall time, use_sim_time:=false. Do not publish simulated clock, simulated odometry, or ground-truth object poses.

real_benchmark_upper.yaml currently publishes to rt/safety/lowcmd_upper_in, not final rt/lowcmd. It still hardcodes eno1 and includes reactive_counter_balance; its name does not establish approval for the Counter adapter's effective settings. Require an operator-approved common configuration with the appropriate Counter section. Never substitute counter_safety_split.yaml, a domain-1 simulation profile, merely because an environment variable overrides its domain. Reject any alternate upper config that writes directly to final rt/lowcmd; do not run it alongside safety.

05 / Terminals

Only after operator preflight: use a clean native zsh terminal on each host, with Conda and any previous venv inactive. Remove inherited foreign Python/Conda overlays by opening a clean shell, not by copying another machine's paths. Set this host's GOLEM_ROOT first. The following setup intentionally joins the hardware domain; it is not an observation permission bypass.

Require every setup line to succeed before continuing. Use local_setup.zsh, not a copied setup.zsh underlay chain. Bash users use the corresponding .bash setup files in a clean bash shell. The function invokes the actual ROS CLI file using ROS Python; no guessed Python __main__ module is used. Do not activate Controller Python globally or add its NumPy 2 site-packages to ROS vision.

All APPROVED_* variables are mandatory values from the responsible operator, not defaults supplied by this guide. File variables must be absolute, existing, reviewed files on the host running the component. A value being set or a file existing does not grant approval. Do not copy a block until its stated preconditions hold.

06 / Observation

Start no control or gripper drivers in this stage. Require the native driver prerequisites and approved head calibration/serial first. Use a separate prepared terminal for each long-running process. Only one computer publishes robot state and each TF edge.

Onboard / state

The state launch reads joint state and publishes TF; it does not start the arm command server. It has no controller-config launch argument: the joint publisher reads the default safety_split.yaml, whose YAML domain is 1 and interface is empty. The exported hardware domain overrides that domain. Before using this command, the owner must verify the installed default's state topic and that SDK interface selection resolves to the approved NIC. Stop if this cannot be established; this guide does not edit source/configs to resolve it.

Onboard / head camera

This launch sets wall time internally, resets the selected camera and publishes camera TF. Its head transform appears after a 10-second timer; wait for it and verify the correct frame direction. Do not also start a second camera TF publisher. Do not use all of h12_real_drivers.launch.py as an actuator-free camera shortcut: grippers are enabled by default and can move during initialization.

Companion / localizer

First verify the actual color stream, matching CameraInfo intrinsics/distortion and image dimensions, timestamp synchronization and camera-to-pelvis TF. The default compressed subscription is the standard real-camera /realsense/head/color/image_raw/compressed; select raw transport only if that is the approved available stream. Do not relax reprojection, age or ambiguity thresholds to hide failed calibration.

Check sustained freshness, not a single good sample. ROS graph visibility does not establish raw DDS command safety. The localizer publishes observations, not TF or motion commands.

Companion / RViz

Use pelvis as fixed frame. RViz supplies no state, camera or localizer. Inspect actual frame names and the measured grasp frame, not only wrist-link /left_ee_pose or /right_ee_pose, when evaluating a grasp-frame target.

07 / Control Stages

Everything in the following collapsed stage can enable motion, including startup. Complete independent hardware qualification of the selected components and their initialization first. Team approval, the physical E-stop operator, physical start-pose approval and the approved mechanical safety rig must be in place. No automatic engagement or stop-release command is provided.

After hardware qualification / onboard control

Keep the observation components running. Launch control once, in one new onboard terminal. Confirm E-stop status arrives before safety starts; the launch's default delays are 3 seconds for safety and 5 seconds for arms, not readiness proofs. It starts the serial E-stop bridge, safety, and a Counter-capable FrameTaskServer. Counter startup is required for the later comparison endpoint; ordinary /frame_task behavior remains the selected Counter backend, not a switchable Frame trial.

Upper initialization commands both arms and torso through its named startup sequence. Inspect actual poses, fresh state, E-stop/safety status and the initialization completion log before goals. A server appearing in the graph does not prove safe initialization. Do not run a second Frame server beside this one. For a separately approved Frame-only qualification, the owner selects upper_controller:=frame instead, as an alternative startup, not an additional process.

Lower body

Only after physical pose verification and the policy owner's approval, start one lower controller in a separate onboard terminal. This command starts the pre-positioning sequence; it is already actuation. The start_position_verified assertion is not a sensor-based safety check.

The lower node waits for fresh state and safety heartbeat, ramps measured legs toward its pre-pose and waits for operator confirmation when configured to do so. A settle timeout is not approval to proceed. For FAME finetune, lower_start_pos and its upstream two-second ramp are the startup posture; lower_default_pos is a different observation/action reference. Review the actual selected policy's sequence rather than copying another policy's pose.

Do not pre-call, script or chain /lowerbody/confirm_engage. An early confirmation can be recorded. The real lower YAML includes a simulation-band-related setting; its release path can wait for a missing simulation service. The owner must approve real timing and configuration. Never create a mock band service, use a simulator tether/hoist option, or treat service success as balance approval. The operator handles the actual mechanical safety rig under the team's procedure.

Initial motion

Qualify empty-hand single-mode goals first, separately for Frame and Counter, with an inspected path and verified clearance. The small relative example below is not automatically tested or universally safe: it moves 2 cm along pelvis +X from the current left grasp frame, with no requested rotation. Use it only if the owner has approved that exact frame, direction, clearance and backend. Counter can move the opposite arm too. Do not send it as a first blind hardware test or reuse the simulation's large absolute target.

A planned action plans and executes; plan: true is not a preview-only flag. Use the team's independent plan-inspection procedure before authorizing execution. Ordinary FrameTask duration is not a certified overall emergency-stop deadline, and planning/cancellation latency is not instantaneous.

08 / Comparison

Counter planned batches are not yet hardware certified. The new /compare_frame_task action uses custom_ros_messages/action/FrameTask in the same Counter-capable FrameTaskServer process. It is not a second arm controller. Ordinary /frame_task stays unchanged. Rebuild and verify the installed API against this checkout before relying on it.

  • Use plan: true with exactly one arm frame and one pose. The comparison order is the ROS string parameter comparison_order, default frame,counter; CSV duplicates allow frame,counter,counter,frame (ABBA).
  • The batch freezes its order and preparation settings. Change them only while idle. upper_controller is startup-only; do not try to hot-swap it with a parameter command.
  • Both trial conditions use one common approved preparation posture, common configuration and planned moving-arm path. Only the upper trial state resets. The lower standing-policy process/history continues during the same run; do not restart or re-engage it between trials.
  • The batch duration is an overall wall-clock budget, including preparation, planning, replay and settling; zero selects 300 seconds. It is not a guarantee of instant preemption inside a blocking planner or a replacement for the physical E-stop.
  • The FrameTask result contains success; per-trial details belong in the logged comparison summary. The server prints the path to planned-comparison-*.json under ROS_LOG_DIR, or the ROS home log directory (normally ~/.ros/log). step_timing contains work-time and overrun aggregates; its scope excludes observer-callback overhead, so it is not an end-to-end deadline guarantee. Do not infer measured balance benefit, contact success or hardware qualification from action success alone.
After hardware qualification / prepare a later batch

Required progression: qualify both empty-hand single modes; approve and verify the common named prep posture; inspect the common plan; qualify a small Counter trial and effective counter-arm limits; only then authorize ABBA. The default named posture prep is not automatically safe on this robot. APPROVED_PREP_CONFIG must name an existing reviewed named configuration, not a YAML path. Keep the free arm and torso clear throughout.

This only sets parameters; it does not authorize a goal. No hardware batch target is supplied here. After separate hardware qualification, the responsible operator supplies the complete inspected goal YAML, including plan: true, one approved frame/pose, and the whole-batch duration. The following template refuses an unset payload; setting the variable does not replace physical approval.

A relative batch target is defined from the common prepared posture, not a fresh incremental displacement on every trial. One action plans one reference; all conditions in that batch share it. A new comparison action can produce a different plan. Check the installed implementation's semantics and reference hash before comparing results.

Record order, configuration hashes, software revisions, common-path identity, state freshness, trial start/end errors, counter excursion/velocity, clipping, cancellation/failure status, lower-policy continuity and physical support condition. The same run preserves policy history, but does not make physical trial starts identical or remove order effects. Stop on any failed preparation or trial instead of continuing blindly.

09 / Marker Tasks

Use the same measured marker layout: DICT_4X4_50, ID 7 top-left and ID 8 top-right, each 30 mm black code inside a 40 mm outer square. Mount the paper flush to the top and adjacent side edges of the 320 x 250 mm board, with unchanged orientation and full 5 mm white border. Nominal centres are (-140, 105) and (140, 105) mm in board-local X/Y. PnP uses the black 30 mm edge, not the paper size. Confirm actual print scale, mounting, board orientation, holes and active peg geometry physically.

Never use marker_profile_sim_extraction.json on the real robot. Its 0.03465 gripper service compensation and 0.1786 distal geometry belong to the simulation extraction calibration. Neither that file nor nominal marker_profile.json is a real grasp calibration. Supply a physically verified real profile with the active peg and named source hole matched to the actual board.

Calibrate camera extrinsics, TCP/grasp-frame transforms and physical gripper command units against the real hardware. The shipped head transform documents about +/-13 mm and 1.5 degrees uncertainty and should be treated as a stale profile until recalibrated for this setup. Matching CameraInfo and low reprojection error do not eliminate extrinsic or TCP error. Micron-level peg/hole clearance claims need metrology; precision insertion is not implemented or demonstrated by this workflow.

Catalog suffixes 0..3 describe clearance rows, not four peg sizes. A skill profile must match the real active peg, source hole and physical seating. Verify the named source actually contains the expected peg; a restored source is an operator assumption until physically checked. A previous extraction can leave source-consumption state in the skills process. Restarting software does not restore a peg.

After hardware qualification / grippers and marker skills

Complete physical gripper qualification, calibration and port ownership first, with fingers clear. The existing launch contains per-side device IDs and angle calibration; use it only if those exact identities and values have been approved for the attached hardware. Start it once on the onboard host, outside the control launch, not also through full real drivers.

Then, in a separate companion terminal, start marker skills only after the motion endpoints, gripper endpoints, fresh localizer and physically calibrated real profile are approved. Check the profile exists on this host before using it. Starting servers does not authorize sending a grasp goal.

Hardware extraction requires its own staged acceptance: unloaded approach, verified TCP clearance, calibrated contact/force limits, supervised closure and controlled lift. No automatic peg-extraction or insertion goal is supplied here. Do not run marker skills concurrently with a comparison batch or another upper-arm action client.

10 / Stop and Record

  1. For an emergency, use the tested physical E-stop and the team's hardware emergency procedure. ROS action cancellation, Ctrl+C, and safety software are not independent emergency stops. Do not improvise E-stop release or power removal while the robot is unsupported.
  2. For a normal stop, stop issuing goals and follow the approved support/hold and payload procedure first. Ctrl+C on an action client does not guarantee the server-side goal stopped; cancellation may wait for planning or execution checks, and a last command can remain held.
  3. With the robot physically secured and the approved shutdown sequence active, use Ctrl+C to stop skill clients/servers and the assigned control components, then wait for their children to exit. The safety/lower/upper stop order and hardware power sequence must be specified by the team, not guessed from terminal order.
  4. Stop observation, camera and RViz processes when their data is no longer needed. Confirm no command writers remain by the approved hardware/DDS method before the team's power sequence. Never restart a controller without repeating pose, state, E-stop and clearance checks.
  5. Keep logs, comparison summaries, configuration/calibration hashes, software revisions, policy/checkpoint identity, architecture, device identities, effective limits, operator approvals and the mechanical support condition. Label every result as offline, simulation, rig-qualified or freestanding hardware; do not combine those claims.
