Native Linux / ROS 2 Humble / Real robot

H1-2 Real
Task Guide

Start the measured workcell, launch one arm controller, engage the approved standing policy, then grasp or extract. Switch Frame/Counter and reuse an approach between tasks without restarting standing.

This is an operator procedure template; no hardware commands were executed to validate it. Use the team's approved hardware, policies, calibration and stop procedure. Commands below use native ROS on the hardware bus, never simulation helpers.

01 / Prepare and Preflight

  1. Assign an operator and a person holding the tested physical E-stop; verify the safety rig, exclusion area and stop/power procedure.
  2. Verify the supported physical start pose, empty hands, feet, arm paths and whole free-arm workspace.
  3. Verify hardware NIC/DDS configuration, device identities, permissions, timestamp synchronization and wall-time state/TF/camera data on both hosts.
  4. Assign exactly one final rt/lowcmd writer, the safety relay. Approve the matching real upper/safety YAMLs, joint mappings, gains, limits and stale-data behavior; upper and lower controllers publish only their split safety inputs.
  5. Approve the real lower policy/config and the physically calibrated marker/gripper profile matched to the seated source. No simulation gripper compensation or simulation safety profile belongs on hardware.

Use a clean native bash or zsh terminal per long-running component. Set GOLEM_ROOT to this host's absolute checkout path, then prepare every terminal:

Require every setup line to succeed. In bash, use the corresponding setup.bash and local_setup.bash. Keep ROS/vision on ROS Python and arms/joint-state publishing on Controller Python through the explicit prefixes below. Every APPROVED_* value is supplied by the responsible operator; file values are absolute, existing files on the component's host.

Build once, before hardware power or connection

Provide ROS 2 Humble, Python 3.10 and environments/ros/apt-packages.txt prerequisites, submodules and Git-LFS assets. Check host architecture before setup: pinned binary dependencies must support that architecture; do not copy absolute-path venvs/install trees from another computer.

The experiment build is not a hardware-driver installer. Provide approved cl_realsense/realsense2_camera, librealsense, image-transport plugins, physical Magpie/Dynamixel dependencies, udev permissions and E-stop serial setup separately. Verify the head-camera serial and gripper device IDs in their launch files.

02 / Start the Workcell

Hardware replaces the simulation scene. Use the real 320 x 250 mm board, with the expected cylinder_1 seated at source cylinder_1. Match the real profile to the board, source pose, TCP and physical gripper units. Keep the workcell fixed and verify table/board clearance along the whole approach.

Start each component once, in a separate prepared terminal. Onboard owns state/TF and devices; the companion owns geometric localization and skills. If an approved driver process already supplies one component, do not launch its duplicate.

Wait for head-camera TF (the camera launch has a 10-second transform timer), matching CameraInfo and fresh valid board diagnostics. The state publisher's default DDS reader must resolve to the approved NIC/state topic; exporting domain 0 does not select a NIC. No simulator, /clock or ground-truth object publisher is used.

Marker print layout and optional RViz

Use DICT_4X4_50, ID 7 top-left and ID 8 top-right. Each 30 mm black code sits on a 40 mm paper square with a full 5 mm white border. Mount paper flush to the top and adjacent board side edges without changing orientation: centres (-140, 105) and (140, 105) mm in board-local X/Y. PnP uses the black-code edge, not paper size. Use an ArUco print generator, measure printed scale and check the shared layout; catalog suffixes 0..3 mean clearance rows, not peg sizes.

Use pelvis as fixed frame. Compare actual grasp-frame TF, head RGB and board diagnostics, not a stale pose arrow or wrist-link pose. This marker path needs no cloud models or AI API keys.

03 / Launch Controller

After preflight, start the onboard control block once. This creates one Counter-capable arm server, initially in Frame mode, plus the E-stop bridge and safety relay. Startup moves arms and torso; wait for actual E-stop/safety readiness and completed initialization, not just elapsed launch delays.

Require the initialized-server log and measured poses after init_1, init_2, init_3, home and torso initialization. These are plain named-posture moves. Do not also run either full real bringup: the onboard full launch starts upper initialization even when its lower-body start_position_verified gate is false.

Lower startup already pre-positions joints. Use the approved real configuration with engage_wait_for_confirm: true and disable_elastic_band: false: despite its name, enabling the latter requests a simulator band-toggle service and can leave a hardware run waiting for a service that does not exist. The physical rig follows the team's procedure, not a simulated tether command.

Never use marker_profile_sim_extraction.json, counter_safety_split.yaml or an unreviewed nominal marker profile on hardware. An exported domain does not turn a simulation configuration into a real one.

04 / Engage Lower Body

Wait for initialized upper control, settled legs and the confirmation prompt. With approved physical support, clear arm sweep and the E-stop operator ready, finish moving the arms home before releasing support:

Wait for success and verify measured home, actual leg posture, support and fresh state/safety heartbeat. A commanded pose or startup warning is not measured convergence; do not continue after a settle timeout. Explicitly engage:

Do not pre-call or chain this service to launch. Follow the approved physical support procedure and wait for stable standing before arm goals. A successful service response is not measured balance. If posture is unstable or state/safety becomes stale, stop using the physical safety procedure and record the actual failure reason.

05 / Choose Frame or Counter

Use the same controller, node and task topics in either mode. Counter may move the opposite arm: keep that hand empty and its entire swept space clear. Select only between whole finished tasks:

For Frame, use ros_cli param set /frame_task_server control_mode frame. Setting a mode does not move the robot; busy changes are rejected. Do not restart the controller/lower policy or change gains, configuration or parameters during a goal.

06 / Grasp or Extract

Verify the source peg is seated, the real profile matches it, and the complete path is clear. Default approach_mode=plan performs ordinary named preparation, acquires a fresh ArUco board snapshot, plans one approach, executes it, then contacts and grasps. The named prep and tool geometry must be approved for this fixture; self-collision planning does not model arbitrary table/board obstacles.

Choose one task from a freshly seated source. The recipe is identical in Frame or Counter mode. Pick/place includes its own grasp; do not call it after grasp-only.

B / Extract and hold

Marker pick/place does not insert or release. Its top_down path requires 90 degrees internally; min_downward_pitch_deg exists only on SkillGrasp. Keep visual_servo: false. Verify contact and actual extraction/retention rather than inferring them from action success.

The bounded trajectory uses the accepted start snapshot, so markers need not remain visible behind the hand throughout motion. Joint, limit, reached-target and cancellation guards remain active. On failure, stop issuing goals, keep the reported cause and inspect the held posture/payload. Cancellation is not an E-stop or automatic withdrawal.

07 / Return and Reuse

Keep standing and both controllers running. For grasp-only, verify the peg remains seated and supported, then open with the approved physical aperture before returning:

After extraction, secure and physically restore the peg to its original seated source under the approved fixture procedure before repeating. Never open a loaded hand blindly or move the fixture around an actively moving robot. Return with empty hands and a checked path:

Wait for success. This is the home for the recorded approach, not ordinary home, which may differ from its prepared start. It does not reset the lower body or restore objects.

Optionally switch control_mode while idle, recheck the restored source/workcell, then send the same task goal. Reuse checks a fresh observation against existing workcell bounds but keeps the original task target snapshot and saved path. A wrong measured start is rejected, not automatically returned.

For a changed scene/task, set ros_cli param set /h12_skills approach_mode plan and plan again. A new plan replaces the old cache. The path and snapshot are RAM-only and do not survive controller/skills restarts. Each explicit goal assumes the operator has restored and checked its input scenario.

08 / Stop and Details

For danger or unexpected motion, use the tested physical E-stop and approved hardware emergency procedure. For normal shutdown, stop issuing goals, secure the payload and robot, then follow the team's support/control/power sequence. ROS cancellation and Ctrl+C are not independent emergency stops; the last command may remain held and no automatic retreat is promised.

Keep task result/failure text, measured motion, software/configuration/profile revisions, checkpoint identity and physical support condition. Do not claim a standing or grasp result from action/service success alone.

Manual single-arm plan and replay

Ordinary /frame_task retains its one-goal behavior; plan: true there plans and executes. For a separate empty-hand manual task, supply one inspected hardware approach goal to the plan-only endpoint:

Plan-only stores one path without moving. Replay needs no target; it checks current start/path and uses stored timing without replanning. Return through approach_start before repeating it. Named planning and ordinary planned carry goals do not overwrite the explicit cache; a new explicit plan does. Duration is a wall-clock execution budget, not requested movement time. The runtime adapter paces on wall time.

Component references and failed acquisition

If board acquisition fails, read /perception/pegboard/diagnostics and check print layout, CameraInfo, timestamp synchronization and TF at the image stamp. Do not loosen bounds or tune gains to bypass a rejected goal.

The control, lower-body and state blocks are the command sources. The real lower YAML is a review starting point, not an approval substitute.

Root run_simulation.sh, run_controller.sh, run_ros.sh and run_rviz.sh are simulation-only and reject domain 0. Do not bypass those guards or run a simulator on the robot bus.
