Native Linux / MuJoCo / ROS 2 Humble

H1-2 Simulation
Operations Guide

Prepare the isolated environments, choose Frame or Counter, and extract a seated peg using a calibrated, supported simulation workflow. All commands start from the GOLEM repository root.

Simulation only. Use ROS_DOMAIN_ID=1. The native launchers refuse domain 0, the real robot bus. This guide does not cover hardware deployment. Offline checks and available policy files do not prove balance, safe motion, or successful grasping.

01 / What Runs Where

The simulator, ROS processes, and arm controller use separate Python environments. The root scripts choose the correct interpreter and ROS overlays. Do not activate these environments manually or combine their Python paths.

Environment roles
EnvironmentNumerical stackRole
environments/rosNumPy 1ROS CLI, safety, lower-body policy node, geometric ArUco localization, and marker skills.
environments/controllerNumPy 2Isolated Pinocchio/Pink/OMPL arm controller and joint-state publisher. Experiment bringup selects either Frame or Counter; both expose the same ROS actions.
environments/simulatorNumPy 2 / MuJoCo 3.3.1PegInHole physics, viewer, cameras, grippers, clock, and DDS/ROS bridges.

This marker workflow uses camera geometry and the local asset catalog. The ArUco localizer lives in model_server, but does not load its AI models. It does not need AI API keys, SAM weights, or cloud calls. Compressed image transport means JPEG camera delivery, not an AI motion prior. The native environment does not install RoboCasa kitchen scenes.

Keep ground-truth odometry off for this workflow. Localization comes from the head camera, its calibration, and timestamped TF, not simulator object poses.

02 / Prepare Each Terminal

Use a normal user shell, including zsh. If Conda is active, deactivate it first; repeat the deactivation if environments are nested. Skip that command when Conda is not installed or no environment is active.

The wrappers work directly from zsh or bash. Stay at the repository root and use the paths below; do not source ROS setup files, activate a venv, or manually alter PYTHONPATH or library paths. Display credentials are preserved by the wrappers, not repaired by them.

03 / First-Time Setup and Build

Complete this once for a prepared checkout, and repeat the relevant build/check after dependency, interface, or source changes. These commands prepare files and run offline checks; they do not start simulator loops or ROS nodes.

Prerequisites

  • Linux with ROS 2 Humble under /opt/ros/humble and system Python 3.10 at /usr/bin/python3.
  • Initialized repository submodules and downloaded Git-LFS assets, including the H1-2 model, ManipulationNet catalog, and bundled standing policies.
  • The system packages listed in environments/ros/apt-packages.txt: build tools, CMake, Python development/colcon tools, ROS generators, rclpy, cv_bridge, and standard messages. A working OpenGL stack is needed for rendering; RViz also needs an installed rviz2 and a working desktop display.
  • Access to the locked dependency downloads during setup. Setup runs as your normal user and does not install system packages or invoke sudo. Have an administrator provide missing system prerequisites rather than running the whole setup as root.

--local-ros-debs downloads and extracts only two allowlisted ROS packages, ros-humble-rosidl-generator-dds-idl and ros-humble-nav2-msgs, into the local environment. It is not a general apt installer or a replacement for ROS Humble.

Build the experiment profile, which selects 12 packages, with two parallel compile jobs. Build it before setting up the controller: the controller check needs the generated interfaces.

The controller setup installs its locked dependencies, including those needed by Counter. Repeat controller setup and the experiment workspace build after changing controller dependencies or launch files; do not manually install another version into the environment. The interface step builds message-only Livox support from the pinned checkout. It does not install a hardware driver or resynchronize the simulator dependencies.

Require successful checks before continuing. They check imports, generated interfaces, and offline numerical/bridge operations. They do not qualify standing performance, camera visibility during motion, contact physics, or insertion accuracy. Everyday launch commands do not install or compile anything.

04 / Configure the Scene

The default task is PegInHole, with a level table and board on the robot's left and one cylinder_1 peg seated in cylinder_1. The board origin is approximately (0.504, 0.185, 0.955) metres in the scene world frame. The board footprint is 0.32 x 0.25 m; its entry surface is 25 mm above its origin.

Scene and localization defaults
SettingDefault / meaning
Task--task PegInHole
Active peg and seated source--peg cylinder_1 --source-hole cylinder_1
MarkersDICT_4X4_50: ID 7 top-left, ID 8 top-right. Mount each 40 mm paper square flush with the board's top and adjacent outer side edge; no inset. Keep the printed orientation unchanged.
Marker dimensions30 mm black square, 40 mm total white-paper square. PnP uses the black-square edge, not the paper edge.
Localization cameraHead color image and CameraInfo. The PegInHole helper selects full profiled 1280 × 720 resolution by default.

Catalog suffixes 0..3 are clearance rows, top-to-bottom from tight to loose. They are not four peg sizes or scale factors: the source peg geometry is shared across a shape's rows. For example, cylinder_3 names the looser destination row, not a larger cylinder.

On the 320 × 250 mm board, flush paper edges place marker centres at board-local (X, Y) = (−140, 105) mm and (140, 105) mm: 280 mm centre-to-centre. Retain the full 5 mm white border around each 30 mm black code. The shared layout file defines these offsets for both rendering and localization. Accurate mounting helps repeatability but does not remove print-scale, camera-calibration or pose-estimation error.

The simulator can select catalog peg/source IDs, but the skills' active-peg profile must match the physical scene exactly. A different source hole requires an explicitly prepared matching profile, supplied with marker_profile_path:=/absolute/path/to/profile.json. Merely changing simulator flags does not update that profile. Catalog fit checks do not provide a grasp calibration. The extraction workflow below explicitly loads a simulator-only cylinder calibration instead of relying on the nominal profile.

This custom scene is an alternative to the normal run, not a second simulator. Prepare a matching skill profile before using skills. Existing --layout, --style, and --seed options remain available; peg/source flags remain specific to PegInHole.

Camera defaults

The defaults apply to PegInHole through run_simulation.sh; other tasks keep their existing defaults. Explicitly exported GOLEM_CAMERA_* values still take precedence for advanced use. Change settings only before starting a fresh simulator.

05 / Run Frame or Counter

Main workflow: supported manipulation. Keep the translational tether and pelvis rotational hoist enabled, select ALMI for the initial pose and lower-body pre-positioning, and leave its policy unengaged. This is the support condition used for the demonstrated extraction. It is not autonomous standing. Complete Terminal A, choose exactly one Terminal B command, then perform the initialization checks before sending any goal.

Terminal A / start the simulator first

The explicit --lowerbody almi_manip_stand selects only the simulator's initial joint pose and pelvis fit, from the first twelve default_angles in the ALMI source configuration. It does not load a checkpoint, infer a policy, start a controller, or confirm engagement. Without --lowerbody, the root helper preserves the exact legacy baked spawn; it does not infer the ROS policy. Pelvis heading is independent of toe yaw; existing obstacle-clearance placement can still translate the base. Check the printed selection and actual fit logs: a source configuration pose is not a guarantee of balanced or flat-footed standing.

Leave this terminal running. --manipulation-hoist explicitly selects the existing pelvis rotational support, stiffness 2000 N m/rad and damping 12 N m s/rad, alongside the startup translational band. It is opt-in; omitting it does not reproduce the extraction support condition. Verify the seated peg, elastic band on torso anchored at ..., and the logged pelvis rotational hold. Support is not proof of a safe pose or stable balance.

Without a display / choose this instead of the GUI simulator

Keep the same support and controller choices. Start only one simulator; do not run this alongside the GUI command.

To inspect performance, add --timing to the simulator command. It logs real-time factor and stage timings every five wall-clock seconds. A real-time factor of 1 means one simulated second per wall-clock second; 0.5 means the simulation takes twice as long. Check other CPU/GPU workloads and the reported stage costs before changing sensor output or physics settings. Start only one simulator.

Keep the startup tether enabled. Do not press Space or manually toggle the band to bypass engagement. If the robot is not held in the expected safe posture, stop before starting actuation.

Optional video / select this instead of the simulator command above

Ensure ~/Downloads already exists and choose an unused output name. Recording also writes an evaluation-only JSONL sidecar; it does not supply ground truth to the robot stack. Stop the simulator cleanly after the experiment so recording can finalize.

Playback is 1x simulation time, not evidence of wall-clock real-time performance. The camera/viewer image and evaluation sidecar do not replace physical contact and clearance checks.

Terminal B / choose one upper controller

Run Frame OR Counter, never both. Each command starts one complete experiment bringup, including state/TF, localization, safety, one upper controller, ALMI pre-positioning, and marker skills. Do not leave observation-only bringup running alongside either command. To compare controllers, use a fresh simulator and repeat the same support, lower-body selection, initialization, and goal.

Alternative A / Frame baseline

After visually verifying the held start posture and clear workspace, explicitly allow actuation. start_position_verified:=true is the operator's assertion, not an automated safety check.

Frame is the ordinary task-space baseline and the controller used for the successful supported extraction. For a one-arm task, it retains the other arm's ordinary hold behavior.

Alternative B / Counter experiment

Counter uses the existing robust-3C nominal controller, CounterDDPVelocityRobustController, through a small CounterFrameController adapter. It does not select the separate H2/H3 benchmark variants. The selector loads the matching controller configuration; the upstream safety relay remains unchanged.

Counter uses the same /frame_task and /named_config interface. A single-frame, single-arm target leaves the opposite arm available for counter-motion; multi-frame goals are rejected in Counter mode. Do not constrain both arms or put an object in the free hand when testing that behavior. Its presence is not proof of successful tracking, contact, or improved balance.

Initialization / required for either controller

  1. Keep the simulator supported. Check fresh state and safety heartbeat; stop on stale control data or unexpected motion.
  2. Wait for init_1, init_2, init_3, home, then torso yaw initialization. Require Frame Task Server initialized and fresh end-effector poses. Initialization uses plain named postures in both modes, not counter-motion.
  3. Wait for legs pre-posed (settled, ...) and the lower-body confirmation prompt. A NOT SETTLED (timeout) message is not permission to continue. Inspect actual arm/leg posture and clearance, not only action-server availability or initialization logs.
  4. Do not call /lowerbody/confirm_engage for this supported demo. Leave ALMI holding its pre-pose and leave both support mechanisms enabled. Proceed to the direct-arm staging command and then choose one marker skill.

Select ALMI independently in both terminals: simulator syntax is --lowerbody almi_manip_stand, ROS syntax is lowerbody:=almi_manip_stand. Neither launcher selects the other terminal's policy. Starting the lower-body node permits pre-positioning before confirmation; unengaged does not mean no motor commands.

Observation only / alternative to all actuated bringup

This starts state/TF and localization only. Stop it and wait for its children to exit before selecting Frame or Counter. It cannot execute the arm or skill commands below.

Optional FAME selection and startup behavior

For FAME, independently select ./scripts/run_simulation.sh --task PegInHole --lowerbody fame_finetune in Terminal A and ./scripts/run_experiment.sh start_position_verified:=true lowerbody:=fame_finetune in Terminal B, instead of the ALMI commands. The simulator uses the source configuration's lower_start_pos, not a training default, and only fits the initial joints/pelvis. It does not start or confirm the controller. With a fixed pelvis orientation, the asymmetric FAME pose can leave unequal sole gaps; inspect actual fit logs rather than assuming both feet are exactly flat. Controller pre-positioning follows the upstream deployment sequence: interpolate the measured legs to lower_start_pos over two seconds, then hold that startup posture for operator confirmation. The separate lower_default_pos remains the reference for policy observations and actions; it is not a replacement startup pose.

For either policy, torso yaw is owned by the upper-body controller, not by the twelve-leg-joint policy.

These end-effector topics report wrist-link poses, not the GRASPGENX origin used by the staging goal. Use the named grasp-frame TF in RViz or the active /frame_poses output to inspect that goal's actual controlled frame; do not compare a wrist position directly with a GRASPGENX target.

Separate later experiment / engage the standing policy

This is not part of the extraction recipe. Policy engagement changes the support condition and requires its own supervised balance experiment, with appropriate tether/hoist handling. Finish initialization, require settled legs, and verify actual posture and workspace before any confirmation. Do not manually remove support to bypass the interlock. An engaged policy with a rotational hoist is still not an unsupported balance test.

The service can record an early confirmation. Never pre-call it or chain it into launch. It starts the selected 50 Hz standing policy and initiates its tether-release sequence; a successful response is not evidence of balance. Do not combine this test with an unverified grasp or controller comparison.

06 / View and Inspect

Use another prepared terminal for RViz after the simulator and one bringup mode are running. The viewer does not replace bringup and should not start a second localizer.

The launcher starts only the RViz client, on simulation time, with pelvis as its fixed frame. Its source-checkout default is core_ws/src/h12_bringup/rviz/pegboard.rviz, derived from GOLEM's existing full h12_bringup/rviz/main.rviz recipe. The original main.rviz and standard bringup use_rviz defaults are unchanged. A working display and installed RViz are required. Use --config PATH for a different RViz configuration.

RViz alone does not publish a robot, TF, or camera images. If those displays have no data, check that the simulator and exactly one experiment bringup are running; enabling a display cannot replace its publisher. The prerequisite check below checks files and launcher dependencies, not live topic readiness or rendering performance.

How to interpret localization diagnostics
SignalMeaning and operator check
valid=true, level OKThe current image/calibration/TF and geometric quality checks accepted a board observation. This does not verify a grasp or guarantee collision clearance.
Waiting for image/calibrationLocalization needs synchronized camera data. Confirm camera topics, advancing simulation time, and matching CameraInfo.
No usable marker or ambiguous poseCheck marker visibility, image resolution, marker IDs, layout, and viewpoint. Either marker can localize the board if its pose passes the quality checks; both need not be visible. Do not infer validity from marker count or a rendered model alone.
Reprojection / geometry rejectionThe image estimate did not meet configured quality bounds. Check calibration and layout; do not loosen bounds simply to enable motion.
Observation TF pendingThe localizer is waiting within a bounded interval for the camera-to-pelvis transform at the original image timestamp. Check one bringup's TF and simulation-time configuration if it persists. It does not substitute the latest TF.
Stale observation / clock resetThe last estimate is no longer safe to use. Default pose-age limits are 0.5 seconds of ROS time. With use_sim_time=true, a slow simulator is evaluated on its simulation clock, not on wall-time delivery gaps. Real-time operation also retains a monotonic receipt-age check. Goal execution deadlines remain wall-clock limits. Restart all ROS processes and RViz after a simulation clock reset.

Inspect observation age and the status message, not only a persistent pose arrow. Input age, processing wall time, and pending-TF count help separate camera delivery, processing, and transform readiness. Low reprojection error is image consistency, not millimetre-level insertion accuracy. A previously drawn pose may remain visible after localization becomes invalid. Skills require fresh valid observations and reject excessive board jumps.

07 / Direct Arm Commands

Use Terminal C only with one verified actuated bringup, after upper-body initialization, settled lower-body pre-positioning, and inspection of the supported posture. Policy engagement is not required for the supported workflow. Run one goal at a time and wait for its result. Do not run these demonstrations concurrently with a marker skill or while holding a peg. Inspect the whole path and the other arm's clearance first.

Stage the left task arm / Frame extraction preparation

Use these three actions in order from a fresh supported Frame run. Wait for SUCCEEDED after each action and inspect actual clearance. Preparation bends the arms first, establishes the documented pitch-down orientation at a certified workspace point, then moves the left hand aside for the camera. Do not skip a stage or continue after an aborted goal. Positions are in metres in pelvis; quaternions are ROS XYZW order. This staging sequence is not a qualified Counter extraction sequence.

All three preparation actions have completed in supported testing with sub-millimetre final staging error. Require valid localization again after moving aside. This verifies preparation, not a subsequent grasp: the moving hand can still hide markers during the skill. Do not continue on an invalid observation or weaken the visibility checks to make it run.

See Counter motion / same task in both modes

  1. Start a fresh supported Frame run and complete initialization. Run the planned prep posture below, wait for success, then send the small relative left-arm move. Observe both arms in the simulator or RViz RobotModel.
  2. Stop and reset using section 09. Start Counter instead, with the same ALMI pre-pose and tether/hoist, then repeat the same preparation and relative move. Keep the right arm clear, empty, and absent from frame_names.
  3. Check Upper controller: counter (CounterFrameController) at startup and Upper controller goal: balanced moving=left, counter=right for the one-sided goal. Inspect measured motion, not merely an accepted goal or commanded targets. The left arm must still reach its task. Inspect the right arm during that task, not during named-pose initialization.

Use another prepared terminal for inspection while the action runs, then Ctrl+C the inspection CLI. Do not repeatedly send the +50 mm goal: each accepted relative goal adds another offset. The matched supported check above completed successfully in both modes:

The clearest response in this check was the right shoulder-pitch joint, with the right elbow also moving. The Frame right-arm command stayed fixed; its measured drift is not counter control. Counter produced both commanded and measured right-arm motion. Both command arrays stayed fixed during the recorded post-success hold; there was no commanded return posture. This validates a small supported counter-response task, not Counter extraction, cancellation behavior, or improved standing balance. The hoist masks balance outcomes. A nearly stationary free arm on another small move does not by itself prove Counter is disabled.

This check uses each backend's existing stock configuration. The Frame and Counter configurations have different control rates, limits and planning bounds. The same task and support make the functional check useful, but it is not a controlled performance comparison. Match the common configuration settings before a later benchmark; do not interpret the small error difference as an algorithm ranking.

Named configuration / choose one

home and prep are actual named configurations. They are posture examples, not universally collision-free moves. These two commands are alternatives, not a required sequence. Named postures command both arms using plain posture control, including when Counter is selected: a prep move is not evidence of counter-motion. Duration zero selects the server's configured timeout.

Small relative frame move

This requests a 20 mm upward offset for right_graspgenx_frame, measured along pelvis-frame Z, with no orientation change. It is plan: false and slow_mode: true. Relative offsets use pelvis axes, not tool-local axes.

Duration is a timeout, not a trajectory duration. For both actions, the server interprets a positive duration as the allowed wall-clock execution time; zero uses the server default. It does not force a 30-second movement. Slow mode reduces commanded speed. Planning checks modeled joint/self-collision constraints, not board or table avoidance, grip physics, or arbitrary scene obstacles. Check actual measured motion and scene clearance.

Do not publish direct motor commands to bypass the controller and safety pipeline. Gripper opening is not part of these examples: opening while holding a peg can drop it, and a skill-owned hold must not be overridden casually.

08 / Calibrated Peg Extraction

Procedure: fresh default cylinder_1 scene, translational tether plus pelvis rotational hoist, Frame bringup with lowerbody:=almi_manip_stand, the explicit profile below, completed upper initialization, settled ALMI pre-pose without engagement, valid camera localization, then all three preparation actions in section 07. Finally run one of the two alternatives below. The reference extraction uses source and destination cylinder_1, not a transfer to cylinder_3. Continuous marker visibility remains a qualification requirement; reaching the preparation poses does not guarantee that a fresh extraction will complete.

Simulator calibration only, not hardware calibration. Load core_ws/src/h12_skills/h12_skills/marker_profile_sim_extraction.json through the Terminal B command. Its GRASPGENX contact offset is [0, 0.002238, 0.1786] m, not the nominal 0.1146 m axial offset. Its aperture_margin_m=0.03465097 compensates the simulated gripper service mapping; it is not a physical jaw-clearance margin. Do not copy these values onto the robot or substitute the nominal profile and expect the same grasp.

The profile matches the 12 mm diameter, 50 mm long cylinder seated at cylinder_1. It requests a 50 mm approach, 60 mm board-normal extraction, and a final nominal tip height 40 mm above the selected entry. Keep image_transport:=compressed for full-resolution JPEG camera delivery. Require fresh valid localization diagnostics before the goal; the skills continue checking freshness during motion. Inspect the entire left-arm path, table/board clearance, and free arm.

Choose one alternative from a reset. Do not run grasp-only and then pick/place. Pick/place already includes its own grasp. Once close is dispatched, the skills treat the source pose as consumed or uncertain, even if the goal later fails. Reset the simulator and restart skills before another attempt; restarting skills alone does not restore the peg.

Alternative A / grasp only

Approaches the calibrated seated source, commands close, and holds there. It does not extract the peg. A successful action result means the commanded sequence completed; it is not independent contact or grip verification.

Alternative B / full extraction and retained pre-insertion hold

Includes grasp, board-normal extraction, carry/pre-insertion stages, and a retained hold above the same hole. The nominal tip target is 40 mm above the entry, assuming a rigid grasp. It does not insert or release. Do not open the gripper or issue another posture goal afterward. A later transfer to cylinder_3 is a different experiment, not the demonstrated extraction recipe.

Keep visual_servo: false: marker mode has no AI servo. top_down: true requires a geometric vertical approach. SkillGrasp additionally exposes min_downward_pitch_deg, set to 90 above; SkillPickPlace has no such goal field and enforces the top-down 90-degree requirement internally. The calibrated left GRASPGENX orientation is pelvis-fixed RPY (180, 0, 30) degrees. Hole/contact positions follow the observed board pose; the contact offset is transformed using this tool orientation. Extraction and pre-insertion offsets follow the board normal. A nonvertical top-down profile fails closed rather than relaxing the pitch.

What counts as success

The reference supported Frame run physically extracted and retained the peg. Independent post-run checks over 100 hold snapshots found both finger pads in contact throughout, no non-hand peg contacts or active peg weld, at least 49.5 mm whole-collision-mesh clearance above the board, and less than 0.8 mm hand-relative position drift. These measurements describe that run, not a guarantee for every restart or a Counter result. No simulator ground-truth measurements were fed back to the controller.

The documented three-stage preparation is separately verified. A complete extraction from that fresh-start sequence is not yet repeatably qualified: the left forearm can occlude the markers during pregrasp, and the skill then cancels before closing. Inspect the head-camera view throughout the approach. The reference physical success and the supported Counter response must not be interpreted as resolving this visibility limitation.

Judge your run by actual peg motion and retained contact, not just SUCCEEDED, a rendered target, or a recorder classifier flag. The generic recorder's physical_extraction_candidate was false in the reference run because its 0.25 m hand-body proximity test excluded the distal-pad grip approximately 0.289 m from that origin. That heuristic is not independent grip verification; do not change thresholds merely to obtain a positive label.

Optional right-arm geometry example / not the extraction recipe

This command does not move the board or change workspace limits. The default left fixture may be outside the right arm's admission limits; changing the arm in the goal does not select a right-side scene. The analysis boxes describe fingertip grasp-frame positions, not GRASPGENX origins, and are certified subsets rather than exhaustive reachability bounds. Use an explicit arm. Workspace admission, measured frame checks, board freshness, and planner results do not replace physics validation or actual clearance checks. On failure there is no guaranteed automatic retreat or release; inspect the scene before deciding how to stop and reset.

A message such as pregrasp canceled: ... identifies a skill guard that canceled the inner arm action; read the cause after the colon. waypoint not reached without a guard cause indicates an unsuccessful controller action and needs its controller feedback. Neither message means the selected arm is prohibited. Do not issue another goal until the preceding action has stopped and the current pose and visibility have been inspected.

09 / Stop and Reset

  1. Stop issuing goals. Do not assume Ctrl+C on an action CLI cancels its server-side motion, or open a loaded gripper as a shortcut.
  2. Stop experiment bringup/controllers in Terminal B with Ctrl+C and wait for its child processes to exit. Keep the simulator running during controller shutdown.
  3. Stop RViz and any remaining ROS CLI or inspection processes.
  4. Stop the simulator in Terminal A with Ctrl+C.
  5. For a new attempt, launch the simulator again, then one bringup mode and RViz. Repeat initialization and held-posture checks. For supported extraction, keep the tether/hoist and do not confirm policy engagement. Any separate engagement experiment needs a fresh operator check and confirmation.

A simulator restart resets simulation time. Restart all ROS processes and RViz with it so timestamped TF and perception caches do not span clock epochs. Restarting the experiment also clears the skills' consumed-source cache. There is no reset-service command in this workflow.
