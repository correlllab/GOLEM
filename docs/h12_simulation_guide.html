Native Linux / MuJoCo / ROS 2 Humble

H1-2 Simulation
Operations Guide

Prepare the isolated environments, inspect the pegboard through the robot camera, and run explicitly gated manipulation experiments. All commands start from the GOLEM repository root.

Simulation only. Use ROS_DOMAIN_ID=1. The native launchers refuse domain 0, the real robot bus. This guide does not cover hardware deployment. Offline checks and available policy files do not prove balance, safe motion, or successful grasping.

01 / What Runs Where

The simulator, ROS processes, and arm controller use separate Python environments. The root scripts choose the correct interpreter and ROS overlays. Do not activate these environments manually or combine their Python paths.

Environment roles
EnvironmentNumerical stackRole
environments/rosNumPy 1ROS CLI, safety, lower-body policy node, geometric ArUco localization, and marker skills.
environments/controllerNumPy 2Isolated Pinocchio/Pink/OMPL arm controller and joint-state publisher, selected by experiment bringup.
environments/simulatorNumPy 2 / MuJoCo 3.3.1PegInHole physics, viewer, cameras, grippers, clock, and DDS/ROS bridges.

This marker workflow uses camera geometry and the local asset catalog. It does not need AI API keys, SAM weights, or cloud model servers. The native environment does not install RoboCasa kitchen scenes.

Keep ground-truth odometry off for this workflow. Localization comes from the head camera, its calibration, and timestamped TF, not simulator object poses.

02 / Prepare Each Terminal

Use a normal user shell, including zsh. If Conda is active, deactivate it first; repeat the deactivation if environments are nested. Skip that command when Conda is not installed or no environment is active.

The wrappers work directly from zsh or bash. Stay at the repository root and use the paths below; do not source ROS setup files, activate a venv, or manually alter PYTHONPATH or library paths. Display credentials are preserved by the wrappers, not repaired by them.

03 / First-Time Setup and Build

Complete this once for a prepared checkout, and repeat the relevant build/check after dependency, interface, or source changes. These commands prepare files and run offline checks; they do not start simulator loops or ROS nodes.

Prerequisites

  • Linux with ROS 2 Humble under /opt/ros/humble and system Python 3.10 at /usr/bin/python3.
  • Initialized repository submodules and downloaded Git-LFS assets, including the H1-2 model, ManipulationNet catalog, and bundled standing policies.
  • The system packages listed in environments/ros/apt-packages.txt: build tools, CMake, Python development/colcon tools, ROS generators, rclpy, cv_bridge, and standard messages. A working OpenGL stack is needed for rendering; RViz also needs an installed rviz2 and a working desktop display.
  • Access to the locked dependency downloads during setup. Setup runs as your normal user and does not install system packages or invoke sudo. Have an administrator provide missing system prerequisites rather than running the whole setup as root.

--local-ros-debs downloads and extracts only two allowlisted ROS packages, ros-humble-rosidl-generator-dds-idl and ros-humble-nav2-msgs, into the local environment. It is not a general apt installer or a replacement for ROS Humble.

Build the experiment profile, which selects 12 packages, with two parallel compile jobs. Build it before setting up the controller: the controller check needs the generated interfaces.

The interface step builds message-only Livox support from the pinned checkout. It does not install a hardware driver or resynchronize the simulator dependencies.

Require successful checks before continuing. They check imports, generated interfaces, and offline numerical/bridge operations. They do not qualify standing performance, camera visibility during motion, contact physics, or insertion accuracy. Everyday launch commands do not install or compile anything.

04 / Configure the Scene

The default task is PegInHole, with a level table and board on the robot's left and one cylinder_1 peg seated in cylinder_1. The board origin is approximately (0.504, 0.185, 0.955) metres in the scene world frame. The board footprint is 0.32 x 0.25 m; its entry surface is 25 mm above its origin.

Scene and localization defaults
SettingDefault / meaning
Task--task PegInHole
Active peg and seated source--peg cylinder_1 --source-hole cylinder_1
MarkersDICT_4X4_50: ID 7 top-left, ID 8 top-right. Mount each 40 mm paper square flush with the board's top and adjacent outer side edge; no inset. Keep the printed orientation unchanged.
Marker dimensions30 mm black square, 40 mm total white-paper square. PnP uses the black-square edge, not the paper edge.
Localization cameraHead color image and CameraInfo. The PegInHole helper selects full profiled 1280 × 720 resolution by default.
Skill profilecore_ws/src/h12_skills/h12_skills/marker_profile.json; active cylinder_1 at source cylinder_1.

Catalog suffixes 0..3 are clearance rows, top-to-bottom from tight to loose. They are not four peg sizes or scale factors: the source peg geometry is shared across a shape's rows. For example, cylinder_3 names the looser destination row, not a larger cylinder.

On the 320 × 250 mm board, flush paper edges place marker centres at board-local (X, Y) = (−140, 105) mm and (140, 105) mm: 280 mm centre-to-centre. Retain the full 5 mm white border around each 30 mm black code. The shared layout file defines these offsets for both rendering and localization. Accurate mounting helps repeatability but does not remove print-scale, camera-calibration or pose-estimation error.

The simulator can select catalog peg/source IDs, but the skills' active-peg profile must match the physical scene exactly. A different source hole requires an explicitly prepared matching profile, supplied with marker_profile_path:=/absolute/path/to/profile.json. Merely changing simulator flags does not update that profile. Catalog fit checks do not provide a grasp calibration: the marker backend supports only cylinder grasps with its nominal profile.

This custom scene is an alternative to the normal run, not a second simulator. Prepare a matching skill profile before using skills. Existing --layout, --style, and --seed options remain available; peg/source flags remain specific to PegInHole.

Camera defaults

The PegInHole launch helper selects the camera settings for marker manipulation. Use the plain command in the next section; no inline camera variables are needed. The effective settings are printed at startup.

SettingDefaultPurpose
GOLEM_CAMERA_SCALE1Render at full profiled resolution, not an enlarged low-resolution image. This improves corner detection for the 30 mm markers; CameraInfo intrinsics match the rendering resolution.
GOLEM_CAMERA_DEPTH0Disable the standalone depth/image_rect_raw stream. Marker localization uses RGB and CameraInfo.
GOLEM_CAMERA_POINTCLOUD0Disable camera depth/color/points streams, which this experiment does not use.

RGB, CameraInfo, camera TF, aligned depth and Livox LiDAR remain enabled. This is not a complete depth-rendering shutdown or a change to physics timing. The defaults apply to PegInHole through run_simulation.sh; other tasks keep their existing defaults. Explicitly exported GOLEM_CAMERA_* values still take precedence for advanced use. Change settings only before starting a fresh simulator.

05 / Everyday Run

Terminal A / start the simulator first

The explicit --lowerbody almi_manip_stand selects only the simulator's initial joint pose and pelvis fit, from the first twelve default_angles in the ALMI source configuration. It does not load a checkpoint, infer a policy, start a controller, or confirm engagement. Without --lowerbody, the root helper preserves the exact legacy baked spawn; it does not infer the ROS policy. Pelvis heading is independent of toe yaw; existing obstacle-clearance placement can still translate the base. Check the printed selection and actual fit logs: a source configuration pose is not a guarantee of balanced or flat-footed standing.

Leave this terminal running. Without a display, use ./scripts/run_simulation.sh --task PegInHole --lowerbody almi_manip_stand --headless instead of starting a second simulator. Verify the scene, the intended seated peg, and the startup message elastic band on torso anchored at .... The startup tether holds the robot while controllers initialize; a tether is not proof of a safe pose or stable balance.

To inspect performance, add --timing to the simulator command. It logs real-time factor and stage timings every five wall-clock seconds. A real-time factor of 1 means one simulated second per wall-clock second; 0.5 means the simulation takes twice as long. Check other CPU/GPU workloads and the reported stage costs before changing sensor output or physics settings. Start only one simulator.

Keep the startup tether enabled. Do not press Space or manually toggle the band to bypass engagement. If the robot is not held in the expected safe posture, stop before starting actuation.

Terminal B / choose one bringup mode

The two modes below are alternatives in the same terminal. Stop the previous bringup with Ctrl+C and wait for its child processes to exit before starting the other. Do not run two localizers, state publishers, or TF trees against the same simulator.

Alternative A / observation only

Starts joint/robot state publishing and the geometric ArUco localizer on simulation time. It does not start safety-command merging, the arm controller, the lower-body controller, or skill action servers. Use this mode to inspect images, TF, and localization while the simulator is tethered.

Alternative B / explicitly allow actuation

Use only after operator approval and visual verification of the simulator's held start posture and clear arm workspace. The flag below is an operator assertion, not an automated safety check. Stop observation-only bringup first.

almi_manip_stand is the standard policy used throughout this guide. Select the same policy independently in both terminals: simulator syntax is --lowerbody almi_manip_stand, ROS syntax is lowerbody:=almi_manip_stand. Neither launcher automatically selects the other terminal's policy. Do not launch both policies. This mode also starts safety, upper-body control, lower-body control, and marker skill servers. Arm initialization and lower-body pre-positioning can move joints before policy engagement.

  1. Keep the simulator running and tethered. Check fresh state and safety heartbeat, and monitor both terminals for rejected or stale control data.
  2. Wait for the arm startup sequence init_1, init_2, init_3, home, then torso yaw initialization to the configured zero target. Joint-convergence warnings report residual error without terminating the controller or skipping torso initialization. Require Frame Task Server initialized and fresh end-effector poses. Do not confirm the lower body during arm initialization.
  3. Verify the actual home/staging posture and clearance in the viewer, not just the presence of an action server. If an intended staging move is required, complete and inspect it while safely held before proceeding.
  4. Wait for the lower-body prompt reporting legs pre-posed (settled, ...) and waiting for confirmation. A NOT SETTLED (timeout) prompt is not permission to proceed. Verify the safe held posture again.
  5. Only then use Terminal C for the separate confirmation call below. The controller runs the manipulation standing policy at 50 Hz and handles tether release after commitment; monitor the resulting logs and motion. Do not send arm/skill goals until the resulting posture is steady and safe.
Optional FAME selection and startup behavior

For FAME, independently select ./scripts/run_simulation.sh --task PegInHole --lowerbody fame_finetune in Terminal A and ./scripts/run_experiment.sh start_position_verified:=true lowerbody:=fame_finetune in Terminal B, instead of the ALMI commands. The simulator uses the source configuration's lower_start_pos, not a training default, and only fits the initial joints/pelvis. It does not start or confirm the controller. With a fixed pelvis orientation, the asymmetric FAME pose can leave unequal sole gaps; inspect actual fit logs rather than assuming both feet are exactly flat. Controller pre-positioning follows the upstream deployment sequence: interpolate the measured legs to lower_start_pos over two seconds, then hold that startup posture for operator confirmation. The separate lower_default_pos remains the reference for policy observations and actions; it is not a replacement startup pose.

For either policy, torso yaw is owned by the upper-body controller, not by the twelve-leg-joint policy.

The confirmation service can record an early confirmation. Do not pre-call it, put it in a launch chain, or treat a successful response as proof of balance. Operators must verify initialization, settling, tether state, and clearance before calling it.

06 / View and Inspect

Use another prepared terminal for RViz after the simulator and one bringup mode are running. The viewer does not replace bringup and should not start a second localizer.

The launcher starts only the RViz client, on simulation time, with pelvis as its fixed frame. Its source-checkout default is core_ws/src/h12_bringup/rviz/pegboard.rviz, derived from GOLEM's existing full h12_bringup/rviz/main.rviz recipe. The original main.rviz and standard bringup use_rviz defaults are unchanged. A working display and installed RViz are required. Use --config PATH for a different RViz configuration.

RViz alone does not publish a robot, TF, or camera images. If those displays have no data, check that the simulator and exactly one experiment bringup are running; enabling a display cannot replace its publisher. The prerequisite check below checks files and launcher dependencies, not live topic readiness or rendering performance.

How to interpret localization diagnostics
SignalMeaning and operator check
valid=true, level OKThe current image/calibration/TF and geometric quality checks accepted a board observation. This does not verify a grasp or guarantee collision clearance.
Waiting for image/calibrationLocalization needs synchronized camera data. Confirm camera topics, advancing simulation time, and matching CameraInfo.
No usable marker or ambiguous poseCheck marker visibility, image resolution, marker IDs, layout, and viewpoint. Either marker can localize the board if its pose passes the quality checks; both need not be visible. Do not infer validity from marker count or a rendered model alone.
Reprojection / geometry rejectionThe image estimate did not meet configured quality bounds. Check calibration and layout; do not loosen bounds simply to enable motion.
Observation TF pendingThe localizer is waiting within a bounded interval for the camera-to-pelvis transform at the original image timestamp. Check one bringup's TF and simulation-time configuration if it persists. It does not substitute the latest TF.
Stale observation / clock resetThe last estimate is no longer safe to use. Default pose-age limits are 0.5 seconds of ROS time. With use_sim_time=true, a slow simulator is evaluated on its simulation clock, not on wall-time delivery gaps. Real-time operation also retains a monotonic receipt-age check. Goal execution deadlines remain wall-clock limits. Restart all ROS processes and RViz after a simulation clock reset.

Inspect observation age and the status message, not only a persistent pose arrow. Input age, processing wall time, and pending-TF count help separate camera delivery, processing, and transform readiness. Low reprojection error is image consistency, not millimetre-level insertion accuracy. A previously drawn pose may remain visible after localization becomes invalid. Skills require fresh valid observations and reject excessive board jumps.

07 / Direct Arm Commands

Use Terminal C only in verified actuated mode, after initialization and engagement checks. Run one goal at a time and wait for its result. Do not run these demonstrations concurrently with a marker skill or while holding a peg. Inspect the whole path and the other arm's clearance first.

Named configuration / choose one

home and prep are actual named configurations. They are posture examples, not universally collision-free moves. These two commands are alternatives, not a required sequence. Duration zero selects the server's configured timeout.

Small relative frame move

This requests a 20 mm upward offset for right_graspgenx_frame, measured along pelvis-frame Z, with no orientation change. It is plan: false and slow_mode: true. Relative offsets use pelvis axes, not tool-local axes.

Duration is a timeout, not a trajectory duration. For both actions, the server interprets a positive duration as the allowed wall-clock execution time; zero uses the server default. It does not force a 30-second movement. Slow mode reduces commanded speed, but neither slow mode nor planning validates contact physics. Check actual measured motion and scene clearance.

Do not publish direct motor commands to bypass the controller and safety pipeline. Gripper opening is not part of these examples: opening while holding a peg can drop it, and a skill-owned hold must not be overridden casually.

08 / Marker Manipulation Skills

Start from a fresh scene with the default seated cylinder_1, a matching active-peg profile, fresh valid board localization, and an initialized, safely engaged robot. Check the left-arm approach, board, table, and destination clearance. The catalog profile is nominal simulation geometry, not measured grip calibration.

Choose one alternative from a reset. Do not run grasp-only and then pick/place. Pick/place already includes its own grasp. Once close is dispatched, the skills treat the source pose as consumed or uncertain, even if the goal later fails. Reset the simulator and restart skills before another attempt; restarting skills alone does not restore the peg.

Alternative A / grasp only

Approaches the catalog-derived seated source, commands close, and holds there. It does not extract the peg. A successful result means the nominal sequence completed; it is not independent contact or grip verification.

Alternative B / full grasp-to-pre-insertion sequence

Includes grasp, board-normal extraction, free-space carry, and a final pre-insertion hold. With the default profile, the peg tip stops 40 mm above the destination entry, assuming a rigid grasp. It does not insert, release, or verify that the peg is actually held. In marker mode this deliberately narrower behavior overrides the generic action name's implication of a full placement.

Keep visual_servo: false: marker mode has no AI servo. top_down: true selects the arm-specific geometric 90-degree-down profile from h12_ros2_controller/docs/workspace_analysis/head_camera.json, with pelvis-fixed grasp-frame RPY left (0, 90, -60) and right (0, 90, +60). These convert to pelvis-fixed GRASPGENX RPY (180, 0, 30) and (180, 0, 150), respectively, because its +Z, not grasp-frame +X, is the approach axis. Hole and contact positions track the observed board pose, while orientation and the pregrasp approach remain pelvis-fixed. The nominal contact remains 0.1146 m along GRASPGENX +Z; its offset is subtracted after transforming the contact into pelvis. Extraction and pre-insertion offsets follow the board normal. Explicit top-down requires 90 degrees in pelvis even when the requested minimum defaults to zero; board tilt/noise does not reduce that pitch, but a nonvertical top-down profile fails closed.

This command does not move the board or change workspace limits. The default left fixture may be outside the right arm's admission limits; changing the arm in the goal does not select a right-side scene. The analysis boxes describe fingertip grasp-frame positions, not GRASPGENX origins, and are certified subsets rather than exhaustive reachability bounds. Use an explicit arm. Workspace admission, measured frame checks, board freshness, and planner results do not replace physics validation or actual clearance checks. On failure there is no guaranteed automatic retreat or release; inspect the scene before deciding how to stop and reset.

A message such as pregrasp canceled: ... identifies a skill guard that canceled the inner arm action; read the cause after the colon. waypoint not reached without a guard cause indicates an unsuccessful controller action and needs its controller feedback. Neither message means the selected arm is prohibited. Do not issue another goal until the preceding action has stopped and the current pose and visibility have been inspected.

09 / Stop and Reset

  1. Stop issuing goals. Do not assume Ctrl+C on an action CLI cancels its server-side motion, or open a loaded gripper as a shortcut.
  2. Stop experiment bringup/controllers in Terminal B with Ctrl+C and wait for its child processes to exit. Keep the simulator running during controller shutdown.
  3. Stop RViz and any remaining ROS CLI or inspection processes.
  4. Stop the simulator in Terminal A with Ctrl+C.
  5. For a new attempt, launch the simulator again, then one bringup mode and RViz. Repeat the initialization and operator engagement checks; do not reuse an earlier confirmation.

A simulator restart resets simulation time. Restart all ROS processes and RViz with it so timestamped TF and perception caches do not span clock epochs. Restarting the experiment also clears the skills' consumed-source cache. There is no reset-service command in this workflow.
